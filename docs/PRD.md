# Obsidian T3 Code 产品需求文档 (PRD)

> **项目名称**：Obsidian T3 Code
> **文档版本**：v1.0.0 (MVP 阶段定义)  
> **状态**：评审中 (Under Review)  
> **维护责任人**：Obsidian T3 Code 团队（产品经理 & 技术负责人）
> **基线日期**：2026-11-18

---

## 1. 项目背景

Obsidian 作为以“本地优先（Local-First）”、“双向链接”和 Markdown 为核心的顶级个人知识库（PKM），拥有数以百万计的研究者、开发者与创作者。然而，现有绝大部分 Obsidian AI 插件主要依赖单次文本补全 API，缺乏真正的 Agentic 软件工程能力（无法自主规划、无法利用多模型/多智能体编排、缺乏安全沙箱隔离与严谨测试）。

与此同时，**T3 Code** 已经构建了工业级的多智能体编排平台，原生支持由 ChatGPT 账号授权的 **Codex**、Google Antigravity 与 Claude 等顶尖编程 Agent，具备完整的 Git Worktree 隔离、MCP 工具生态与任务委派能力。

**Obsidian T3 Code 的核心使命**：以极度轻量、安全、原生的方式，将 T3 Code 的自主 Agent（优先接入 Codex）引入 Obsidian，赋能知识库的深度对话、智能检索与内容共创。

## 2. 目标用户与使用画像

| 角色画像 | 核心痛点 | 典型场景 |
| :--- | :--- | :--- |
| **重度 Obsidian 开发者** | 在 Obsidian 记录技术架构与方案，但需要频繁跳出笔记去 IDE 或网页终端提问。 | 在编辑技术设计笔记时，直接呼出 Agent 依据当前上下文分析技术方案，并将代码建议一键插入笔记。 |
| **知识学者 / 深度思考者** | 收集了大量相关主题笔记，需要对零散知识进行跨文档交叉检验、归纳总结。 | 选中当前笔记的核心章节，向 Agent 提问并要求梳理出逻辑大纲与论证瑕疵。 |
| **安全敏感型用户** | 担心未经验证的 AI 脚本未经允许直接覆写、污染自己多年的重要知识库资产。 | 要求 Agent 的所有读写行为均可控、可预览，严禁直接后台篡改 Markdown 文件。 |

## 3. 核心问题与产品定位

### 3.1 核心问题
1. **割裂的上下文**：外部 AI 工具无法无缝感知 Obsidian 当前打开的笔记与高亮选区。
2. **环境复杂度过高**：在笔记插件内如果盲目启动庞大的 Node 守护进程或重写 Agent 引擎，会导致内存暴增、Windows 路径报错、进程僵死。
3. **数据安全性隐患**：缺少安全隔离层时，Agent 的文件写入容易导致用户笔记内容丢失或 Git 冲突。

### 3.2 产品定位
- **定位**：专注于 Obsidian 知识流与 T3 Code Agent 引擎之间的高性能、轻量化桥梁。
- **架构哲学**：**“轻量客户端，后端重计算，安全第一，原生体验”**。

## 4. 用户故事 (User Stories)

- **US-01（连接建立）**：作为用户，我安装并启用插件后，输入本地 T3 Code 地址或配对码，即可秒级建立安全双向长连接，无需配置繁琐的 API Key。
- **US-02（上下文提问）**：作为用户，在阅读或编写某篇笔记时，我能在侧边栏向 Codex 提问，Agent 能自动识别并带上当前活动笔记的标题、内容或选中文字。
- **US-03（流式交互）**：作为用户，我能实时看到 Agent 逐字生成的思考链路与回复内容，并能在中途随时点击“停止”。
- **US-04（会话管理）**：作为用户，我可以新建对话、切换历史对话，且对话内容与状态不会因 Obsidian 标签页切换而丢失。
- **US-05（结果采纳）**：作为用户，在得到满意的 Agent 回答后，我可以一键将结果“插入到当前光标处”或“复制为 Markdown”。

## 5. 功能需求矩阵 (P0 / P1 / P2)

### 5.1 P0：MVP 必须实现（最小闭环）

| 功能模块 | 用户价值 | 使用场景 | 技术依赖 | 开发难度 | 验收标准 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- | :---: | :--- |
| **F-01: 插件生命周期与配置** | 插件在 Obsidian 中稳定加载并支持配置服务连接地址。 | 初次安装配置 | Obsidian Plugin API, `LocalStorage` | 低 | 1. 在 Obsidian 社区插件列表无错误加载；<br>2. 设置页可保存 T3 服务地址（默认 `http://127.0.0.1:3425`）；<br>3. 重启 Obsidian 后配置不丢失。 |

| **F-04: 基于 Codex 的流式对话** | 与 ChatGPT 授权的 Codex 顺畅交流，流式输出回答。 | 发起提问与推理 | T3 Orchestrator V2 (`orchestration.dispatchCommand`, `message.dispatch`) | 中 | 1. 发送 Prompt 后秒级出现流式 Token；<br>2. 支持中途“停止生成（Stop）”；<br>3. 完整支持 Markdown 代码块语法高亮。 |

### 5.3 P2：后续增强（深度生态打通）

- **Multi-Agent 协同透视**：在 Obsidian 中直接观察子 Agent（Swarm）的任务分发与并行状态。
- **Git Worktree 笔记快照隔离**：利用 T3 的 Worktree 能力，为笔记重构实验创建临时分支。
- **移动端全量支持**：适配 iOS / Android 移动端 Obsidian，依托 T3 Connect 远程连接桌面服务。
- **MCP 表单动态渲染 (Elicitation)**：在侧边栏原生渲染 T3 推送的复杂工具交互表单。

## 6. 非功能性需求 (NFR)

1. **绝对安全性（Non-negotiable）**：
   - **Vault 保护**：MVP 阶段对 Vault 笔记的操作仅限“通过只读 API 抓取上下文”与“用户显式点击插入”。严禁在未确认情况下由 Agent 在后台自动化覆写本地任何 Markdown 文件。
   - **隐私保护**：零外泄，除发往用户本地 T3 Code Server 外，不向任何第三方上报笔记数据。
2. **轻量与响应速度**：
   - 插件打包体积控制在 500KB 以内（不打包重型 Node 依赖）。
   - 插件初始化加载时间 `<= 50ms`，UI 交互绝对不得阻塞 Obsidian 主线程。
3. **跨平台与环境鲁棒性**：
   - Windows 11 作为首选一等公民平台测试验证，路径分隔符完美兼容。
   - 遇到网络波动或 T3 Code 重启时，能够自动重试与优雅降级。

## 7. MVP 范围界定与需求边界

经过对参考项目的深入调研，我们对技术边界确立以下明确决策：

### 决策 1：不嵌入 WebView / Iframe
- **结论**：**采用 Obsidian 原生 DOM 与隔离的 Markdown 渲染构建侧边栏 UI**。
- **原因**：Iframe 内嵌的 Web 界面无法继承 Obsidian 的主题样式与快捷键，且与当前编辑器的选区、光标双向联动极其困难。

### 决策 2：插件内不启动独立 T3 Server 进程
- **结论**：**纯客户端架构，连接用户已启动的 T3 Code**。
- **原因**：T3 Server 是一个重型 Effect-TS 运行时。在 Obsidian 插件内部管理其生命周期会带来僵尸进程、Windows 端口冲突和不可控的内存膨胀。通过标准 HTTP/WS 连接到现有 T3 实例是业内验证最优雅的方案。

### 决策 3：服务未启动的优雅阻断
- **结论**：当检测到 `127.0.0.1:<port>` 未就绪时，侧边栏显示“服务未连接”引导卡片，提供“一键重试”与“如何打开 T3 Code”的图文说明，阻断后续发送动作，防止抛出不可控异常。

### 决策 4：插件内部不自理 Skills 与 MCP
- **结论**：**全部委托给 T3 Code 后端**。
- **原因**：T3 Code 与 Codex 本身已支持 Superpowers、本地 Skills 发现与 MCP 工具调用。插件仅负责展示工具执行的文字状态卡片，绝不在插件前端重复造轮子。

## 8. 明确不做的功能清单 (Out of Scope for MVP)

为确保 MVP 在 2~3 周内高质量交付，以下功能明确排除在 MVP 之外：
- ❌ **不做** 笔记文件后台静默自动修改（避免风险）。
- ❌ **不做** 插件内置的本地 LLM 权重运行。
- ❌ **不做** 插件内的 MCP 服务器安装与配置管理后台。
- ❌ **不做** 复杂的 Git Worktree 可视化图谱。
- ❌ **不做** 语音输入与实时音频转录。

## 9. 阶段验收标准 (Definition of Done)

MVP 阶段完成必须同时满足以下 6 项量化标准：
1. **安装校验**：在没有任何开发环境的纯净 Obsidian 测试库中，解压或构建产物能够正常加载无报错。
2. **连接校验**：在本地 T3 Code 运行的情况下，点击“连接”可在 1 秒内建立握手，显示绿色“已连接”状态。
3. **上下文感知校验**：打开一篇测试笔记，选中一段文本，点击侧边栏“引用选区提问”，Prompt 中准确包含所选文本。
4. **Codex 流式生成校验**：向 Codex 发起一个技术问题，侧边栏在 2 秒内开始逐字流式打字输出，Markdown 格式完整无乱码。
5. **采纳校验**：点击“插入当前文档”，生成的回答内容准确无误地追加在当前笔记的光标停留位置。
6. **单元测试与 CI 覆盖**：协议解析、上下文组装逻辑单元测试覆盖率 `100%`，运行 `npm test` 无失败用例。

## 10. 风险与依赖管理

| 风险描述 | 影响度 | 触发概率 | 缓解措施 |
| :--- | :---: | :---: | :--- |
| **本地 T3 Code 端口非默认端口** | 中 | 中 | 设置项中允许用户自定义服务端口（如 `http://127.0.0.1:3425` 或其他自定义端口）。 |
| **Codex 账号授权过期** | 高 | 低 | 捕获 T3 抛出的 Auth 错误状态码，友好提示用户在 T3 Code 桌面端刷新 ChatGPT 授权。 |
| **超长笔记导致 Prompt 溢出** | 中 | 低 | 对附带的笔记正文设定最大字符数阈值（如截取前 8000 字），并在 UI 提示截断。 |
